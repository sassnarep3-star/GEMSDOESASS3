What the portal checks, and why the previous download failed

Submission format, official problem page: single layer, float32, values in [0, 1], EPSG:32611, 100 m cells, same bounds as the training data, and “data outside the bounds is null or nan”.

The file this site previously offered wrote NaN outside the footprint (the literal reading of that sentence). The portal's range check rejected it with “Predicted values must be in range [0, 1]” — NaN is not in [0, 1]. Two independent pieces of evidence say 0.0 is what the organizers expect and accept:

  • the organizer reference solution initialises its output map with np.zeros and writes the result without any nodata tag (repo, notebook cells y_out = np.zeros(y_patches.shape) → predicted_faults_example.tif);
  • the sibling GEMSDOE32 validator records outside_mode:"zeros" → portal_compliant_range:true and outside_mode:"nan" → false for the same dot field (receipt).

Our file therefore: GTiff, 1 band, 3292×3730, float32, EPSG:32611, transform (100, 0, 243350, 0, −100, 4508550), no nodata tag, no NaN anywhere, values exactly {0, 1}, 0 outside the scored footprint. That profile is copied from the file the portal already accepted and scored 0.2778.
