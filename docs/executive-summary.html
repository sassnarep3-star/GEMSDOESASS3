3. Why did 0.2778 score highest? (the answer, with the arithmetic)

The metric is S = TP_w / (TP_w + 0.2·FP_w + 0.8·FN_w), where TP_w credits each withheld fault cell by the best prediction within 300 m. Two facts decide everything:

  1. Mass is charged, recall is worth more. A dot that misses costs 0.2; a withheld cell that no dot reaches costs 0.8. With 5.17 M footprint cells a dot field is always mass-limited, so the score is set by how much of the withheld fault set a given mass can reach — i.e. by enrichment, not by how pretty the field is.
  2. The champion field carries almost no mapping skill. Measured here on its exact 37,654 dot positions: median distance to the nearest catalogue cell is 9.06 pixels (906 m); only 0.7% of its dots are within 300 m of mapped ground and 3.5% within 400 m. Scored against the public catalogue on the spatially blocked holdout it captures 0.35% of withheld catalogue credit while an area-proportional field of the same size captures 2.68% — an enrichment of 0.13, i.e. eight times worse than chance at recovering mapped faults.

So the 0.2778 cannot be explained by the field reproducing mapped structure. Inverting the exact metric gives the two ways to reach 0.2778 with 37,654 dots and the measured coverage:

And the hard ceiling that follows. With no enrichment at all (ε = 1) the same arithmetic caps any dot field at about 0.04, whatever the dot count — the model grid in score_estimate_20261030.json peaks at 0.0408 for a blind field at 60k dots. That is why every submission that ignores structure lands in the same 0.01–0.09 band, why the nine focus files cluster at 0.245–0.278 (they all share one support), and why the leaderboard top (0.4544 as fetched on 2026-10-30) sits far above the whole family.

Can we generate something above 0.2778? Yes, conditionally: this release is built to be at least as good as the champion under the selection reading (44,923 dots, 17.1% coverage, tip-continuation support, same mass discipline) and it is the only file in this repository that passes every gate this workspace can run. It cannot be shown to beat 0.2778 without the withheld labels, which are login-walled. The concrete way to beat it is in §6.

5. How to submit (exact steps, no interpretation needed)

  1. Download gemsdoesass3-tipcont-disp44923-4px-20261030T0330Z.tif (or the ZIP, which contains the same single GeoTIFF). Check the SHA-256 above.
  2. Optional re-check on the day: python scripts/validate_submission_tif.py docs/downloads/gemsdoesass3-tipcont-disp44923-4px-20261030T0330Z.tif — it must print all_hard_checks_pass: true. The raster has no NaN, no nodata, every value in [0, 1] and nothing but 0.0 outside the official footprint, so the portal error "Predicted values must be in range [0, 1]" cannot be triggered by it.
  3. Open the submission page, choose the file, paste the note above, submit. The rules allow three submissions a week (official rules PDF) — check the counter first.
  4. Record the receipt. If the score comes back, write it into registry/owner_reported_scores_focus.json as ORGANIZER-CONFIRMED and the estimator can then be calibrated against a real receipt for the first time.

Honest expectation. If the selection reading is right this file lands near the 0.26–0.35 band; if the skill reading is right it lands near 0.09. Both are better than submitting nothing, and the file's support (catalogue continuations) is exactly the kind of prediction the final round's expert panel is asked to verify, which is where the larger prize is decided.

6. What would actually beat 0.2778 — and the leaderboard's 0.4544

  1. Get the feature stack (one download). training_features.tif + labels.tif from the official data page (login). Nothing in this repository, and none of the nine sibling sites, has ever evaluated against those labels; every "holdout" here is a surrogate.
  2. Train a real detector on them. The organizers' own reference solution is a U-Net with a Tversky loss using the same α=0.2/β=0.8 weighting; the leaderboard's 0.34–0.45 cluster is consistent with that class of model.
  3. Then spend slots on the leaderboard, not before. With labels the estimator in score_estimate_20261030.json becomes calibratable and a candidate can be screened before a slot is used.

Until step 1 happens, no submission from this repo can be shown to beat 0.2778, and any claim that it does would be a projection dressed up as a receipt. That is the one thing this document will not do.

8. Irregularities flagged for review (not hidden)

  • IR-SASS3-90 — the literal lane rule is unsatisfiable inside the footprint. The 13GEMSDOE calibration lattice has 206,895 positive cells (4.0% of the footprint) and puts a dot within 3 px of every footprint cell, so the forward reading ">70% of my dots within 3 px of one registry raster" is 99.9% for any field that predicts inside the footprint. The reverse reading (17.2%) and the rank correlation (−0.004) show the released file is not that field. The lattice is a synthetic halo surface, not a submission; the owner must decide whether the rule applies to it.
  • IR-SASS3-91 — owner-reported scores are not receipts. All nine focus scores come from the task prompt. The public leaderboard exposes only the top rows, so they cannot be checked. The estimator is anchored to them and inherits that risk.
  • IR-SASS3-92 — leaderboard figures conflict. The prompt gives 0.4413 and 0.3195 as the top score; the live page fetched on 2026-10-30 shows #1 xiaofanhu 0.4544, #2 0.3916, #3 0.3911. Fetch timestamp is in the receipt.
  • IR-SASS3-93 — the previous candidate's lattice pass was an artefact. The 2026-10-29 file "passed" at 68.99% only because the forward reading was applied to a dispersed field; the same file is 100% covered by the lattice in the forward sense on any other construction. Recorded so the number is not reused.
  • IR-SASS3-94 — GEMSDOE25 and GEMSDOE30 are pixel-identical (44,090 positive cells, xor = 0, different file hashes), both owner-scored 0.2600. The nine-site table therefore contains eight distinct fields, not nine.
  • IR-SASS3-95 — GitHub REST API is rate-limited and the workspace token is invalid (gh auth status: "token in GH_TOKEN is no longer valid"). All fetching in this release uses git over https instead, and every file is SHA-verified against the registry manifest. No push is attempted without working credentials.
